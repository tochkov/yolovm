# Incus and adjacent unit models

Notes the research agent gathered directly on 2026-09-19 while the five sweeps in this folder ran.

## Substrate and adjacent unit models (researched directly)

### Incus (the substrate yolovm wraps)
- **Profiles are Incus's own "default vs override" mechanism.** If no profile is given at launch, the `default` profile is applied; it "defines a network interface and a root disk" and "cannot be renamed or removed". Multiple profiles are applied in the order specified, "so the last profile to specify a specific key takes precedence", and "instance-specific configuration always overrides the configuration coming from the profiles". Config not suitable for the instance type (container vs VM) is silently ignored. Commands: `incus profile create`, `incus profile add <inst> <profile>`, `incus launch <image> <name> --profile <p>`. Source: https://linuxcontainers.org/incus/docs/main/profiles/
- **Network ACLs** are created with `incus network acl create <name>` and attached via the `security.acls` list on a network or NIC. Rules have `action` (allow, allow-stateless, reject, drop) and `state` (enabled, disabled, logged); when ACLs are applied "a default reject rule is added to the NIC", overridable with `security.acls.default.ingress.action` / `security.acls.default.egress.action` (NIC-level beats network-level). ACLs are "available for the OVN NIC type, the OVN network and the Bridge network (with some exceptions)"; the `@internal`/`@external` selectors and ACL groups are OVN-only. Source: https://linuxcontainers.org/incus/docs/main/howto/network_acls/
- **cloud-init hand-off**: keys `cloud-init.user-data`, `cloud-init.vendor-data`, `cloud-init.network-config` (legacy `user.*`). They can be set on profiles or instances; the docs recommend vendor-data in profiles for general defaults and user-data per instance. Only `/cloud` image variants (e.g. `images:debian/12/cloud`) run cloud-init, and "the cloud-init actions are run only once on the first start of the instance". `cloud-init status --wait` blocks until done. Source: https://linuxcontainers.org/incus/docs/main/cloud-init/
- Implication: the "core" tier of yolovm can be expressed almost entirely as Incus profiles (network + ACL + cloud-init vendor-data), and per-VM user choices as instance config, mirroring Incus's own precedence model instead of inventing one.

### Devbox plugins (Jetify) — a compact "install + configure" unit
- A plugin "provides a default Devbox configuration for a Nix package"; it activates automatically when `devbox add <pkg>` matches a plugin name, or explicitly via `include` in `devbox.json` using `"plugin:nginx"`, `"path:./plugin.json"` or `"github:<org>/<repo>?dir=<dir>"` (GitHub plugins are cached 24h). Plugins can define services (`devbox services start|stop`), env vars, and helper config files under `devbox.d/` that users edit and version. Source: https://www.jetify.com/docs/devbox/guides/plugins/
- Manifest (`plugin.json`) fields: `name`, `version`, `description` (shown on activation / `devbox info`), `packages`, `env`, `create_files` (dest→source, templated with `{{ .DevboxDir }}`, `{{ .Virtenv }}`), `shell.init_hook`, `shell.scripts` (`devbox run <name>`), `include` (compose other plugins; later wins). User overrides take precedence over plugin values. There is no explicit "check"/doctor hook in the manifest. Source: https://www.jetify.com/docs/devbox/guides/creating-plugins/

### mise — "core tools" vs registry vs raw backends (a three-tier precedent)
- "Core tools have installation logic built into mise. They do not require a separately installed plugin." Thirteen core tools (Bun, Deno, .NET, Elixir, Erlang, Go, Java, Node.js, Python, Ruby, Rust, Swift, Zig); `core:` prefix forces the built-in over a same-named plugin. Source: https://mise.jdx.dev/core-tools.html
- The registry maps short names to backends by trust tier (packslip; aqua/github/gitlab; language backends like npm/cargo/pipx). Anything not in the registry is still installable with the full backend syntax (`github:owner/repo`, `cargo:name`); new asdf/vfox entries are refused in the registry "for supply-chain security reasons" but remain usable explicitly. Source: https://mise.jdx.dev/registry.html
- Lesson: three concentric rings — built-in (maintainer-owned), curated shorthand (vetted), and "bring your own" (explicit, unvetted) — with the outer ring never blocked, only un-shortened.

### Anthropic sandbox-runtime (srt) — policy-as-config for agent sandboxes
- OS-level sandbox (bubblewrap + seccomp on Linux, Seatbelt on macOS, WFP on Windows alpha) with proxy-based network filtering. Config at `~/.srt-settings.json`: network `allowedDomains` / `deniedDomains` / `allowLocalBinding`; filesystem `allowWrite` / `denyWrite` / `denyRead` / `allowRead`. With no config: "no network access, no writes outside the default write paths, and unrestricted reads". Source: https://github.com/anthropic-experimental/sandbox-runtime
- Lesson: the isolation policy is declared as a small allow/deny document with a secure default, not a menu of modes.

### distrobox-assemble — declarative container manifests as the "pack" boundary
- INI manifest (default `./distrobox.ini`), one section per container with `image`, `additional_packages`, `pre_init_hooks`, `init_hooks`, `exported_apps`, `exported_bins`, `nvidia`, `pull`, `replace`; invoked as `distrobox assemble create|rm [--file]`. Source: https://distrobox.it/usage/distrobox-assemble/

### `flutter doctor` — the reference "doctor" UX
- Official description: "Show information about the installed tooling" (`flutter doctor`), alongside `config`, `channel`, `upgrade`, `precache`. Source: https://docs.flutter.dev/reference/flutter-cli
- Community docs describe the output as per-category lines with a pass mark, a warning mark for potential problems, and a failure mark, each with suggested fixes and `-v` for details (official docs page describing symbols not located; treat symbol details as unverified). Sources: https://www.codecademy.com/article/check-your-flutter-installation-with-flutter-doctor , https://github.com/flutter/flutter/issues/154902

### Login/check verbs the agent tools already expose (for the pack interface)
- **GitHub CLI**: `gh auth status` — "Display active account and authentication state on each known GitHub host... any issues are included in the output"; exits 1 with stderr output when any host has auth issues; `--hostname`, `--active`, `--show-token`; `--json` always exits 0. Source: https://cli.github.com/manual/gh_auth_status
- **Claude Code**: `claude doctor` — "Print read-only installation and settings diagnostics from the terminal without starting a session, including install health, settings-file validation errors, and Remote Control eligibility"; in-session `/doctor` can also apply fixes. `claude auth login` (`--email`, `--sso`, `--console`), `claude auth logout`, `claude auth status` ("Show authentication status as JSON... Exits with code 0 if logged in, 1 if not"). `claude update`, `claude install [version|stable|latest]`. `--dangerously-skip-permissions` is "Equivalent to `--permission-mode bypassPermissions`"; `--permission-mode` accepts `default`, `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions`. `claude remote-control [--name]` starts "a Remote Control server to control Claude Code from Claude.ai or the Claude app. Runs in server mode (no local interactive session)"; `--remote-control-session-name-prefix` defaults to the hostname. Source: https://code.claude.com/docs/en/cli-reference
- **Codex CLI**: `codex login` (browser flow), `codex login --with-api-key` (stdin), `codex login --device-auth` (headless device code), `codex login status`, `codex logout`. Credentials in `~/.codex/auth.json` (or `$CODEX_HOME`), selectable via `cli_auth_credentials_store` = `file` | `keyring` | `auto` | `ephemeral` in `config.toml`; headless options: device auth, copying `auth.json`, or SSH-forwarding `localhost:1455`. Source: https://learn.chatgpt.com/docs/auth (redirect target of https://developers.openai.com/codex/auth)
- Implication: every vendor already ships a `login` and a `status`-style check with a meaningful exit code; a pack's `check` step can wrap these instead of reimplementing them.
