# Core / default / extension lines in four comparable tools

## 1. cloud-init

**Core.** cloud-init calls itself "the industry standard multi-distribution method for cross-platform cloud instance initialization" and "provides the necessary glue between launching a cloud instance and connecting to it so that it works as expected" [src](https://docs.cloud-init.io/en/latest/index.html). The core is a five-stage boot pipeline: Detect (`ds-identify` decides whether cloud-init runs at all), Local (`cloud-init-local.service`, "must block network", finds the datasource, writes network config), Network (`cloud-init-network.service`, runs `cloud_init_modules`, "blocks majority of remaining boot (e.g. SSH and console login)"), Config (`cloud-config.service`, runs `cloud_config_modules` incl. `runcmd`, "blocks nothing"), Final (`cloud-final.service`, runs `cloud_final_modules`, "traditional 'rc.local'") [src](https://docs.cloud-init.io/en/latest/explanation/boot.html). The isolation-boundary analogue is the *datasource* abstraction: "Datasources are sources of configuration data for cloud-init that typically come from the user (i.e., user-data) or come from the cloud that created the configuration drive (i.e., meta-data)"; 31 exist and "users of cloud-init should not have to configure cloud-init to specify which datasource" [src](https://docs.cloud-init.io/en/latest/reference/datasources.html). For local VMs the NoCloud datasource reads `user-data`/`meta-data`/`vendor-data`/`network-config` from a "vfat or iso9660 filesystem ... labelled `CIDATA`", a `ds=nocloud;s=file:///path/` or `s=https://...` kernel argument; `meta-data` "is required to contain an `instance-id`" [src](https://docs.cloud-init.io/en/latest/reference/datasources/nocloud.html). Doctor-like tooling is in core: `cloud-init status` (exit 0 ok / 1 crashed / 2 "recoverable errors"; `--wait` = "Block until cloud-init completes"; `--long` exposes `extended_status`, `errors`, `recoverable_errors`), `cloud-init schema --config-file|--system --annotate` ("Annotate existing cloud-config file with errors on stdout"), `cloud-init analyze blame|show|boot`, `collect-logs`, `query`, and `clean` ("simulate a clean instance") [src](https://docs.cloud-init.io/en/latest/reference/cli.html).

**Default experience.** Nothing to run: distro images ship it enabled ("all major Linux distributions, FreeBSD, NetBSD, OpenBSD and DragonFlyBSD" [src](https://docs.cloud-init.io/en/latest/reference/availability.html); Ubuntu: "installed in the official Ubuntu live server images since the release of 18.04, Ubuntu Cloud Images and also in the official Ubuntu images available on EC2" [src](https://help.ubuntu.com/community/CloudInit)). With no user-data at all the shipped `cloud.cfg` still runs a full default module list — e.g. `cloud_init_modules: seed_random, bootcmd, write_files, growpart, resizefs, disk_setup, mounts, set_hostname, ... users_groups, ssh, set_passwords`; `cloud_config_modules: ... apt_configure, ntp, timezone, ... runcmd, byobu`; `cloud_final_modules: package_update_upgrade_install, ... puppet, chef, ansible, ... scripts_user, ssh_authkey_fingerprints, keys_to_console, ... phone_home, final_message, power_state_change` [src](https://raw.githubusercontent.com/canonical/cloud-init/main/config/cloud.cfg.tmpl). So instances come up "with networking, storage, SSH keys, packages and various other system aspects already configured" [src](https://docs.cloud-init.io/en/latest/index.html). Most modules are no-ops unless their key is present: "Activate only on keys: `runcmd`" / `ansible` / `phone_home` [src](https://docs.cloud-init.io/en/latest/reference/modules.html).

**Extension unit and interface.** Two levels. (a) *User-facing unit* = a user-data part. "Each type is identified by a unique header": `#cloud-config` (`text/cloud-config`), `#!` script (`text/x-shellscript`), `#include` (`text/x-include-url`), `#cloud-boothook`, `#part-handler`, `## template: jinja`, `multipart/mixed` MIME, `#cloud-config-archive`, gzip; the docs split these into formats that "directly configure" (cloud-config, scripts, boothooks) vs containers (include, jinja, MIME, archive, gzip) [src](https://docs.cloud-init.io/en/latest/explanation/format.html). The `#cloud-config` schema covers `package_update`/`package_upgrade`/`packages` (with `[<package>, <version>]`), `runcmd` ("runcmd only runs during the first boot"), `write_files` (`path`, `content`, `owner`, `permissions`, encodings), `users` (`name`, `groups`, `sudo`, `shell`, `ssh_authorized_keys`; "Most of these configuration options will not be honored if the user already exists"), `ssh_authorized_keys` [src](https://docs.cloud-init.io/en/latest/reference/examples.html). (b) *Implementation unit* = a Python module `cloudinit/config/cc_<name>.py` with `handle(name, cfg, cloud, args)`, a `meta` dict (`id`, `distros`, `frequency` in `PER_ALWAYS`/`ONCE`/`PER_INSTANCE`, optional `activate_by_schema_keys`), plus a JSON-schema fragment; "For a module to be run, it must be defined in a module run section in `/etc/cloud/cloud.cfg` or `/etc/cloud/cloud.cfg.d`"; "one can add custom out-of-tree config modules" but "Config modules included in upstream cloud-init benefit from ongoing maintenance" [src](https://docs.cloud-init.io/en/latest/development/module_creation.html). Lifecycle is expressed as frequency, not hooks: "once-per-instance" (write_files, users_groups, ssh, runcmd, apt_configure), "always" (bootcmd, final_message), "once" [src](https://docs.cloud-init.io/en/latest/reference/modules.html); semaphores live at `/var/lib/cloud/instance/sem/config_<module_name>.<frequency>` [src](https://docs.cloud-init.io/en/latest/howto/rerun_cloud_init.html). "First boot" = cached instance-id differs from runtime instance-id (`manual_cache_clean: true` switches to trust mode) [src](https://docs.cloud-init.io/en/latest/explanation/first_boot.html).

**Discovery and distribution.** Module names are "taken directly from the module filename, with the `cc_` prefix and `.py` suffix removed"; ordering is the list order in `cloud.cfg`; a per-entry frequency override uses `- [final_message, once]` (`<name>, <frequency>[, <args>]`) [src](https://docs.cloud-init.io/en/latest/reference/base_config_reference.html). There is no registry or plugin package format; modules are in-tree (or hand-dropped out-of-tree). Config *content* is distributed by the platform (datasource), by URL (`#include`), or by MIME bundling [src](https://docs.cloud-init.io/en/latest/explanation/format.html).

**Overriding defaults.** Priority, decreasing: runtime config from the datasource > image config > builtin defaults; inside image config `/run/cloud-init/cloud.cfg` > `/etc/cloud/cloud.cfg` + `cloud.cfg.d/*.cfg` > hardcoded; "User-provided configurations override settings provided by the platform (called vendor-data)"; user-data can't be modified after initialization [src](https://docs.cloud-init.io/en/latest/explanation/configuration-priority.html). Vendor-data rules are the interesting design: "User-supplied cloud-config is merged over cloud-config from vendor-data"; "Users have ultimate control over vendor-data. They can disable its execution or disable handling of specific parts"; "By default it only runs on first boot"; "If the use of vendor-data is required for the instance to run, then vendor-data should not be used"; vendors must keep it "safe, atomic, idempotent" [src](https://docs.cloud-init.io/en/latest/explanation/vendordata.html).

**Lessons.** First-boot-only is the number-one gotcha: "Most cloud-init configuration is only applied to the system once. This means that simply rebooting the system will only re-run a subset of cloud-init"; re-running needs `cloud-init clean --logs --reboot` ("as if cloud-init never ran") or `cloud-init single --name cc_ssh --frequency always` [src](https://docs.cloud-init.io/en/latest/howto/rerun_cloud_init.html). Debuggability: failures "happen before you can SSH into a machine", invalid YAML may be silently ignored "or log a cryptic parse error", and `clean` on a live box "can create duplicate users or re-run destructive operations" [src](https://oneuptime.com/blog/post/2026-03-02-how-to-debug-cloud-init-issues-on-ubuntu-cloud-instances/view) (secondary source). User sentiment on HN: "I do some basic stuff in cloud-init (which is already frustrating enough)" (pxc); "The YAML structure seems poorly thought out, the documentation is low quality, the iteration loop is tedious" (throwaway894345) [src](https://news.ycombinator.com/item?id=41549935). The project's own answer was to grow the doctor surface (`status --long`, `schema --annotate`, `analyze`, `collect-logs`) rather than shrink the module list [src](https://docs.cloud-init.io/en/latest/howto/debugging.html). Why every image ships it: one image works on every cloud because the datasource layer hides vendor differences and users never pick a datasource [src](https://docs.cloud-init.io/en/latest/reference/datasources.html).

## 2. Ansible

**Core.** Since 2.10 "Ansible consists of two parts: ansible-base, which includes the command line tools with a small selection of plugins and modules, and a set of collections" [src](https://docs.ansible.com/ansible/latest/porting_guides/porting_guide_2.10.html). Today: `ansible-core` "Includes language, runtime, and builtin plugins"; the `ansible` community package "Includes language, runtime, and selected Collections"; core releases "approximately every 6 months, in May and November", the package ships "two major versions ... per year"; mapping: Ansible 2.10/3.x → ansible-base 2.10, 4.x → core 2.11, ... 14.x → core 2.21 [src](https://docs.ansible.com/ansible/latest/reference_appendices/release_and_maintenance.html). The builtin set (`ansible.builtin`, "all modules and plugins contained in ansible-core") is 93 modules (apt, dnf, copy, file, template, service, systemd_service, user, git, get_url, uri, command, shell, lineinfile, package, pip ...), plus 145 filters, 24 lookups, 72 tests [src](https://docs.ansible.com/ansible/latest/collections/ansible/builtin/index.html). Why the split: to "remove the Core maintainers as a bottleneck to community module and plugin development"; "Everything under _core in the ansible.yml migration scenario file will become Ansible 2.10 (ansible-base)" (Sam Doran, 2020-02-19) [src](https://groups.google.com/g/ansible-devel/c/oKqgCeYTs-M/m/cHrOgMw8CAAJ).

**Default experience.** `pip install ansible` gives the batteries-included bundle: ansible 12.0.0 pins 104 collections on ansible-core 2.19.1 [src](https://raw.githubusercontent.com/ansible-community/ansible-build-data/main/12/ansible-12.0.0.deps); each major "accepts the latest released version of each included Collection and the latest released version of ansible-core" [src](https://docs.ansible.com/ansible/latest/reference_appendices/release_and_maintenance.html). Old playbooks keep working ("Your playbooks should continue to work without any changes") but FQCNs are recommended "as some collections may contain duplicate module names" [src](https://docs.ansible.com/ansible/latest/porting_guides/porting_guide_2.10.html). `pip install ansible-core` is the bare-core path.

**Extension unit and interface.** *Role* = directory with `tasks/`, `handlers/`, `defaults/`, `vars/`, `files/`, `templates/`, `meta/`, optional `library/`, `module_utils/`, `*_plugins/`; "You must include at least one of these directories in each role"; `defaults/main.yml` = "very low precedence values for variables provided by the role", `vars/main.yml` = "high precedence variables"; `meta/main.yml` = "metadata for the role, including role dependencies and optional Galaxy metadata" and "Ansible always executes roles listed in dependencies before the role that lists them"; `meta/argument_specs.yml` inserts "a new task ... at the beginning of role execution that will validate the parameters" [src](https://docs.ansible.com/ansible/latest/playbook_guide/playbooks_reuse_roles.html). `ansible-galaxy role init` scaffolds `README.md, defaults/main.yml, files/, handlers/main.yml, meta/main.yml, tasks/main.yml, templates/, tests/, vars/main.yml` [src](https://docs.ansible.com/ansible/latest/galaxy/dev_guide.html). Canonical "install X" role: geerlingguy.docker ("An Ansible Role that installs Docker on Linux", Dependencies: "None") [src](https://github.com/geerlingguy/ansible-role-docker); its whole tunable surface is `defaults/main.yml`: `docker_edition`, `docker_packages`, `docker_packages_state`, `docker_service_manage/state/enabled`, `docker_install_compose_plugin`, `docker_install_compose`, `docker_compose_version`, `docker_add_repo`, `docker_repo_url`, `docker_apt_*`, `docker_yum_*`, `docker_users: []`, `docker_daemon_options: {}` [src](https://raw.githubusercontent.com/geerlingguy/ansible-role-docker/master/defaults/main.yml); `meta/main.yml` carries `role_name`, `min_ansible_version: 2.15.1`, `platforms`, `galaxy_tags`, `dependencies: []` [src](https://raw.githubusercontent.com/geerlingguy/ansible-role-docker/master/meta/main.yml). *Collection* = `galaxy.yml` + `plugins/{modules,inventory,...}` + `roles/` + `playbooks/` + `docs/` + `tests/` + `meta/runtime.yml` (`requires_ansible`, `plugin_routing`); "A collection must have a galaxy.yml file that contains the necessary information to build a collection artifact"; "Roles in a collection cannot contain plugins any more. Plugins must live in the collection plugins directory tree" [src](https://docs.ansible.com/ansible/latest/dev_guide/developing_collections_structure.html). `galaxy.yml` required: `namespace`, `name`, `version` ("Must be compatible with semantic versioning"), `readme`, `authors`, `dependencies` ("Collections that this collection requires ... key ... is the collection label namespace.name"); optional `description`, `license`/`license_file`, `tags`, `repository`, `documentation`, `homepage`, `issues`, `build_ignore`, `manifest` [src](https://docs.ansible.com/ansible/latest/dev_guide/collections_galaxy_meta.html). There are no install/configure/check hooks; a role *is* the install+configure procedure, and "check" is Ansible's idempotent/`--check` semantics.

**Discovery and distribution.** Roles resolve from collections, `roles/` next to the playbook, `roles_path` (`~/.ansible/roles:/usr/share/ansible/roles:/etc/ansible/roles`) [src](https://docs.ansible.com/ansible/latest/playbook_guide/playbooks_reuse_roles.html). One `requirements.yml` lists both `roles:` and `collections:`; role `src` is "namespace.role_name, if downloading from Galaxy; otherwise ... a URL pointing to a repository within a Git based SCM", `version` is "a release tag value, commit hash, or branch name", e.g. `src: git+https://bitbucket.org/willthames/git-ansible-galaxy` [src](https://docs.ansible.com/ansible/latest/galaxy/user_guide.html). Collections: `ansible-galaxy collection install ns.coll:'>=1.0.0,<2.0.0'`, tarball, `git+https://github.com/org/repo.git,devel`, `#/subdir/`; default path `~/.ansible/collections/ansible_collections`; `[galaxy] server_list = my_org_hub, release_galaxy` with per-server `url`/`token`/`auth_url` [src](https://docs.ansible.com/ansible/latest/collections_guide/collections_installing.html). Registries: Galaxy (free, "host collections and roles on Galaxy to share with the Ansible community" [src](https://docs.ansible.com/ansible/latest/galaxy/dev_guide.html)) vs Automation Hub ("a central repository to discover, download, and manage Ansible Content Collections", "Red Hat Ansible Certified Content", "Included with your Red Hat Ansible Automation Platform subscription", plus private hub) [src](https://www.redhat.com/en/technologies/management/ansible/automation-hub).

**Overriding defaults.** A 22-level precedence: role defaults are #2 (just above CLI values), role vars #15, `include_vars` #18, `set_fact` #19, role params #20, extra vars #22 "(always win precedence)" [src](https://docs.ansible.com/ansible/latest/playbook_guide/playbooks_variables.html); "A role's own defaults will take priority over other role's defaults, but any/all other variable sources will override this" [src](https://docs.ansible.com/ansible/latest/playbook_guide/playbooks_reuse_roles.html).

**Lessons.** Bloat is still contested: a 2026 thread on including cisco.catalystcenter ("plugins/ directory size of 26 MB... 1052 action plugins and 1127 modules" plus a 103 MB `cvp/` folder) vs Brian Coca's "size does not become a metric, but general applicability"; the SC can reject content that would "significantly deteriorate the Ansible package user experience" [src](https://forum.ansible.com/t/including-large-specialized-collections-in-ansible-community-package/46222). Practitioners recommend `ansible-core` to avoid "collection bloat" and predict "ansible-core with a well-curated requirements.yml file will become the standard" [src](https://forum.ansible.com/t/removing-collections/38451). Formal removal criteria exist (unmaintained: "No maintainer's activity ... for several months", "CI has stopped passing", bug reports "piling up") [src](https://docs.ansible.com/ansible/latest/community/collection_contributors/collection_package_removal.html). Roles-vs-collections seams: standalone roles cannot declare collection dependencies ("there is no mechanism in Ansible to do this"; sivel: "A standalone role on a standalone role, or a collection on a collection") [src](https://forum.ansible.com/t/specifying-collections-required-by-required-roles/37199); roles in collections lose per-role versions and "cannot have hyphens in the role name"; "You must migrate roles to collections if you want to distribute them as certified Ansible content" [src](https://docs.ansible.com/ansible/latest/dev_guide/migrating_roles.html). Galaxy quality/registry churn: the 2023 Galaxy-NG cutover — "a lot of Galaxy NG was built up around Collections, and Ansible role support was written into the codebase ... after it became obvious Galaxy roles would not be deprecated" [src](https://www.jeffgeerling.com/blog/2023/ansible-galaxy-error-unable-compare-role-versions/) — produced "you can't publish a new version of a role", broken search, and a staff reply that "filtering and sorting are one of the highest priority items" [src](https://forum.ansible.com/t/the-new-galaxy-is-completely-broken/1518).

## 3. Homebrew

**Core.** `brew` itself: "installs each package into its own keg inside the Cellar, then symlinks its files into the prefix" and "won't install files outside its prefix" [src](https://brew.sh/). Default prefixes are fixed per platform (`/opt/homebrew` Apple Silicon, `/usr/local` Intel, `/home/linuxbrew/.linuxbrew` Linux) [src](https://docs.brew.sh/Installation); "/opt/homebrew was chosen to allow installations in /opt/homebrew for Apple Silicon and /usr/local for Rosetta 2 to coexist and use bottles" [src](https://docs.brew.sh/FAQ). Custom prefixes are tolerated only within limits ("must be equal to or shorter in bytes than the platform's default"); Tier 3 means "Homebrew may work, but with a poor and unstable experience" and "maintainers do not commit to fixing bugs" [src](https://docs.brew.sh/Support-Tiers). Doctor is core: `brew doctor` = "Check your system for potential problems. Will exit with a non-zero status if any potential problems are found", but "these warnings are just used to help the Homebrew maintainers with debugging if you file an issue. If everything you use Homebrew for is working fine: please don't worry or file an issue; just ignore this"; `--list-checks` [src](https://docs.brew.sh/Manpage). The ~55 checks (`check_homebrew_prefix`, `check_for_stray_dylibs`, `check_git_status`, `check_deprecated_disabled`, `check_untrusted_taps`, `check_tmpdir`, `check_user_path_1..3`, `check_for_nix_homebrew`...) are non-fatal except `fatal_preinstall_checks = check_access_directories` and `fatal_build_from_source_checks = check_for_installed_developer_tools` [src](https://raw.githubusercontent.com/Homebrew/brew/HEAD/Library/Homebrew/diagnostic.rb). `brew bundle` and `brew services` moved *into* core in 4.5.0: "built-in commands instead of being provided by an external tap" [src](https://brew.sh/2025/04/29/homebrew-4.5.0/).

**Default experience.** "Homebrew/homebrew-core is the default tap" and formulae are "downloaded as JSON from formulae.brew.sh" [src](https://docs.brew.sh/Formula-Cookbook); homebrew-cask is the default cask repo, "extends Homebrew and brings its elegance, simplicity, and speed to the installation and management of prebuilt software artifacts" [src](https://github.com/Homebrew/homebrew-cask). Since 4.0.0 the two default taps aren't even cloned ("Using JSON files downloaded from formulae.brew.sh ... rather than local homebrew/core and homebrew/cask taps"; "you can brew untap homebrew/core and brew untap homebrew/cask to save some space") and auto-update runs "every 24 hours rather than every 5 minutes" because it no longer needs "the slow git fetch of the huge homebrew/core and homebrew/cask taps" [src](https://brew.sh/2023/02/16/homebrew-4.0.0/). "Just works" rests on bottles: "bottled binaries will be used by default except ... Formula options were passed" [src](https://docs.brew.sh/FAQ).

**Extension unit and interface.** *Formula*: a Ruby class subclassing `Formula` (`brew create <URL>`), with `desc`, `homepage`, `url`, `sha256`, `license`, `depends_on`, `conflicts_with`, `def install`, `test do` ("run by brew test foo and BrewTestBot"), `caveats` ("a caveats block can be added to the formula to warn users"), `service do` (launchd/systemd), `livecheck`, `bottle`; post-install must now use declared steps: "Formulae in all taps must represent post-install work with post_install_steps; new post_install methods are rejected" [src](https://docs.brew.sh/Formula-Cookbook); 7.0.0 confirms "post_install and cask *flight Ruby blocks are deprecated in favour of declared *_steps", third-party taps get warnings "until 11 December 2027" [src](https://brew.sh/2026/09/13/homebrew-7.0.0/). *Cask*: declarative stanzas `version`, `sha256`, `url`, `name`, `desc`, `homepage` + at least one artifact (`app`, `pkg`, `binary`, `installer`, `suite`); `uninstall` (`pkgutil:`, `launchctl:`, `quit:`, `signal:`, `script:`, `delete:`/`trash:`) is auto-derived except for `pkg`/`installer`; "The zap stanza describes a more complete uninstallation ... never performed by default, but only if the user uses --zap on uninstall"; `caveats`, `depends_on`, `conflicts_with`, `preflight_steps`/`postflight_steps` [src](https://docs.brew.sh/Cask-Cookbook). So the lifecycle vocabulary is install / post_install_steps / service / test / caveats / uninstall / zap. *Brewfile* is the set-level unit: "Rather than specifying the brew commands you wish to run, you can specify the state you wish to reach" — `tap`, `brew` (`args:`, `restart_service:`, `link:`, `postinstall:`, `version_file:`), `cask`, `mas`, `vscode`, `go`, `cargo`, `uv`, `krew`, `flatpak`, `winget` [src](https://docs.brew.sh/Brew-Bundle-and-Brewfile); `brew bundle` = "Install and upgrade (by default) all dependencies from the Brewfile", `dump` = "Write all installed casks/formulae/images/taps into a Brewfile", `check` = "Check if all dependencies present in the Brewfile are installed", `cleanup` = "Uninstall all dependencies not present in the Brewfile", `--global` reads `$HOMEBREW_BUNDLE_FILE_GLOBAL`, `${XDG_CONFIG_HOME}/homebrew/Brewfile`, `~/.homebrew/Brewfile` or `~/.Brewfile` [src](https://docs.brew.sh/Manpage).

**Discovery and distribution.** "The brew tap command adds repositories that Homebrew can use for formulae, casks and external commands"; `brew tap username/foobar` → `https://github.com/username/homebrew-foobar`; `brew tap <user>/<repository> <URL>` "clones a repository from the specified Git URL without assuming GitHub or a particular transport"; install fully-qualified `brew install username/repository/vim` [src](https://docs.brew.sh/Taps). "A tap is usually a Git repository available online, but you can use anything as long as it's a protocol that Git understands"; formulae go under `Formula/`, `HomebrewFormula/` or the root; "If a formula in your tap has the same name as a Homebrew/homebrew-core formula they cannot be installed side-by-side" [src](https://docs.brew.sh/How-to-Create-and-Maintain-a-Tap). "Tap trust remains the primary protection against malicious third-party casks" [src](https://brew.sh/2026/09/13/homebrew-7.0.0/).

**Overriding defaults.** Deliberately little: "options are not allowed in Homebrew/homebrew-core as they are not tested by CI"; `:optional`/`:recommended` deps likewise banned in core [src](https://docs.brew.sh/Formula-Cookbook). The 2018 proposal "Remove all options from Homebrew/homebrew-core formulae" argued "Options in formulae don't produce a good user experience because they have to be built from source", they aren't CI-tested, and variants belong in taps (nginx example) [src](https://github.com/Homebrew/homebrew-core/issues/31510). Escape hatches are env vars: `HOMEBREW_NO_AUTO_UPDATE`, `HOMEBREW_AUTO_UPDATE_SECS` [src](https://docs.brew.sh/FAQ), `HOMEBREW_NO_INSTALL_FROM_API=1` [src](https://brew.sh/2023/02/16/homebrew-4.0.0/), `HOMEBREW_NO_ANALYTICS=1`/`brew analytics off` [src](https://docs.brew.sh/Analytics).

**Lessons.** Analytics (2016) is the canonical opinionated-default fight: issue #142 "Require analytics opt-in rather than make it a blind default" ("companies and government agencies ... have a problem with data being sent out without explicit permission") [src](https://github.com/Homebrew/brew/issues/142); "Opt-out is never an excuse. It always excludes most users" [src](https://chr4.org/posts/2016-04-26-homebrew-betrayed-us-all-to-google/); McQuaid's reply: "Opt-in gives unrepresentative data", "You will be notified the first time you run brew update or install Homebrew", "We don't have the resources for this" [src](https://news.ycombinator.com/item?id=11566720). Outcome: still opt-out, but "Homebrew displays a notice before analytics are enabled so a user can opt out before sending an event", payload "does not contain a user identifier or an IP-address field", moved to InfluxDB [src](https://docs.brew.sh/Analytics), [src](https://brew.sh/2023/02/16/homebrew-4.0.0/). Auto-update (PR #50, merged 2016-04-11, with `HOMEBREW_NO_AUTO_UPDATE` added before merge) [src](https://github.com/Homebrew/brew/pull/50) still draws issues like #9285: "everytime you install a new package, brew will go ahead and automatically update all of my system packages" [src](https://github.com/Homebrew/brew/issues/9285); the fix was making updates cheap (JSON API) rather than removing the opinion [src](https://brew.sh/2023/02/16/homebrew-4.0.0/). Movement into core: bundle/services (4.5.0) and formal Support Tiers with `brew doctor` linking to them [src](https://brew.sh/2025/04/29/homebrew-4.5.0/); movement out: Intel macOS to Tier 3 [src](https://brew.sh/2026/09/13/homebrew-7.0.0/). Curation rules for core (open source, builds from source, stable upstream tag, not an `.app`, no self-updaters) are explicit [src](https://docs.brew.sh/Acceptable-Formulae).

## 4. Nix home-manager (with NixOS context)

**Core.** "A Nix-powered tool for reproducible management of the contents of users' home directories" [src](https://nix-community.github.io/home-manager/introduction.html); "The module system in Home Manager is based entirely on the NixOS module system" [src](https://nix-community.github.io/home-manager/writing-modules.html). A NixOS module is "a file that handles one logical aspect of the configuration" with `imports`, `options` (declarations) and `config` (definitions); "A module configuration does not have to handle everything from scratch; it can use the functionality provided by other modules" [src](https://raw.githubusercontent.com/NixOS/nixpkgs/master/nixos/doc/manual/development/writing-modules.chapter.md). The bare-core primitives are `home.packages` ("The set of packages to appear in the user environment", default `[]`) [src](https://mynixos.com/home-manager/option/home.packages), `home.file`/`xdg.configFile` symlinks [src](https://wiki.nixos.org/wiki/Home_Manager), and `home.stateVersion` ("It is occasionally necessary for Home Manager to change configuration defaults in a way that is incompatible with stateful data"; enum "18.09" ... "26.11") [src](https://mynixos.com/home-manager/option/home.stateVersion). Three hosting modes: "the standalone home-manager tool. For platforms other than NixOS and Darwin, this is the only available choice"; "a module within a NixOS system configuration ... built together with the system when running nixos-rebuild"; same for nix-darwin/`darwin-rebuild` [src](https://nix-community.github.io/home-manager/installation.html). Note it is a nix-community project, not part of nixpkgs, and warns it "cannot detect whether it will overwrite a previous manual configuration" [src](https://github.com/nix-community/home-manager).

**Default experience.** `nix run home-manager/master -- init --switch` generates a `flake.nix` (`homeConfigurations.jdoe = home-manager.lib.homeManagerConfiguration { pkgs = ...; modules = [ ./home.nix ]; }`) and applies it; then `home-manager switch [--flake ~/hmconf]`; "The flake inputs are not automatically updated by Home Manager" [src](https://nix-community.github.io/home-manager/nix-flakes/standalone.html) (channel path: `nix-channel --add .../home-manager/archive/master.tar.gz home-manager`, `nix-shell '<home-manager>' -A install` [src](https://nix-community.github.io/home-manager/installation/standalone.html)). The minimal config is `home.username`, `home.homeDirectory`, `home.stateVersion = "26.05"`, `programs.home-manager.enable = true` ("Whether to enable Home Manager", i.e. HM manages itself [src](https://mynixos.com/home-manager/option/programs.home-manager.enable)); `home-manager build` previews, `switch` activates [src](https://nix-community.github.io/home-manager/usage/configuration.html). NixOS-flake mode: `home-manager.nixosModules.home-manager`, `useGlobalPkgs`, `useUserPackages`, `home-manager.users.jdoe = ./home.nix`, `nixos-rebuild switch --flake /etc/nixos`, `extraSpecialArgs` to pass flake inputs [src](https://nix-community.github.io/home-manager/nix-flakes/nixos.html).

**Extension unit and interface.** The unit is a module: "The option names of a program module typically start with programs.<package name>. Similarly, for a service module, the names start with services.<package name>" (e.g. `programs.emacs.extraPackages`, `services.gpg-agent.enableSshSupport`) [src](https://nix-community.github.io/home-manager/usage/configuration.html). Install and configure are one thing: `programs.git` declares `enable = mkEnableOption "Git"`, `package = lib.mkPackageOption pkgs "git"`, `signing`, `settings` (`either gitIniType (listOf gitIniType)`), `ignores`, `attributes`, `includes`, `lfs`, `hooks`; under `config = mkIf cfg.enable (` it adds `lib.optionals (cfg.package != null) [ cfg.package ]` to packages and writes `xdg.configFile "git/config"` via `lib.generators.toGitINI`, plus `git/ignore` and `git/attributes` [src](https://raw.githubusercontent.com/nix-community/home-manager/master/modules/programs/git.nix). Conventions: "Home Manager automatically imports all modules from the modules/programs/ and modules/services/ directories"; for structured formats "consider using a settings option as described in Nix RFC 42"; "try to make the package option nullable"; "Less important options should be expressible through an extraConfig escape hatch"; "Every new module must include a named maintainer using the meta.maintainers attribute"; new modules need a news entry [src](https://raw.githubusercontent.com/nix-community/home-manager/master/docs/manual/contributing/guidelines.md). RFC 42's rationale: `extraConfig` strings mean "The defaults can't be changed, multiple values might not get merged properly, inspection of it is almost impossible because it's an opaque string", whereas "with a settings option, it's also very easy to add additional options over time" [src](https://raw.githubusercontent.com/NixOS/rfcs/master/rfcs/0042-config-option.md). There is no explicit check hook; correctness is type-checking at eval time plus module `assertions`.

**Discovery and distribution.** In-repo only: mynixos (unstable) lists 415 `programs.*` and 173 `services.*` option groups [src](https://mynixos.com/home-manager/options/programs), [src](https://mynixos.com/home-manager/options/services); searchable at the manual's options page, extranix (releases unstable, 26.05 stable, 25.11 ...) [src](https://home-manager-options.extranix.com/) and mynixos. Third-party modules arrive as flake inputs added to `modules = [...]`; there is no registry of home-manager modules (unverified beyond the absence of one in the manual).

**Overriding defaults.** "All option definitions that do not have the lowest priority value are discarded. By default, option definitions have priority 100 and option defaults have priority 1500"; `mkDefault` = `mkOverride 1000`, `mkForce` = `mkOverride 50`; list order via `mkOrder` (default 1000; `mkBefore` = 500, `mkAfter` = 1500); `mkIf` pushes conditions "down into the individual definitions"; `mkMerge` combines sets [src](https://raw.githubusercontent.com/NixOS/nixpkgs/master/nixos/doc/manual/development/option-def.section.md). So a "default" layer uses `mkDefault`, a user config overrides silently at 100, and `mkForce` beats a module's hard-coded definition.

**Lessons.** Learning curve: README says "it is quite possible to get difficult to understand errors when working with Home Manager" [src](https://github.com/nix-community/home-manager); HN: "I don't think a beginner should use Home Manager, because that's an extra layer on the already not-beginner-friendly Nix ecosystem" vs "I'm really, really glad I started with Home Manager. It delivered value immediately" [src](https://news.ycombinator.com/item?id=37819217). The install-vs-configure split is official policy: "It is a perfectly valid use case for Home Manager to only install software with home.packages without managing dotfiles at all" [src](https://wiki.nixos.org/wiki/Home_Manager); RFC 42 exists precisely to stop the "every setting needs an option" treadmill [src](https://raw.githubusercontent.com/NixOS/rfcs/master/rfcs/0042-config-option.md). Immutability friction since 2018: "home-manager creates symlinks to read-only files in the nix store which causes problems" for tool-edited files like `.spacemacs`/`.ssh/config` [src](https://github.com/nix-community/home-manager/issues/257); the sanctioned answer is `home.file."file.foo".source = config.lib.file.mkOutOfStoreSymlink "/absolute/path/to/file/to/link";` [src](https://github.com/nix-community/home-manager/wiki/FAQ). A 2024 "Dropping Home-Manager" post lists: mkOutOfStoreSymlink "should not exist ... exists just to 'not break compatibility'", HM "installs itself as a package to your nix profile", "will create backups indefinitely, you can't limit them", "Many things can be configured with both HM and NixOS ... the options may have subtle differences", "The Home Manager CLI is a mess of bash" [src](https://ayats.org/blog/no-home-manager). `stateVersion` is the mechanism that lets defaults evolve without breaking old users [src](https://mynixos.com/home-manager/option/home.stateVersion).

## Cross-tool patterns (my synthesis, not sourced)

- Every tool that stayed usable has a *single curated default source* (homebrew-core, the `ansible` bundle, cloud.cfg's module list, HM's in-repo modules) plus a *cheap escape hatch for everything else* (taps, `requirements.yml` git URLs, out-of-tree `cc_*.py`, extra flake modules).
- Extension units that worked encode *lifecycle as declarative data* (formula stanzas, module `frequency`, `mkIf cfg.enable`) rather than free-form hook scripts; the one hook-shaped API (Homebrew `post_install`) was just replaced by declared `post_install_steps`.
- Overrides are layered with explicit priorities (vendor-data < user-data; role defaults < everything; `mkDefault` 1000 < 100 < `mkForce` 50) and defaults are removable by the user (vendor-data "can be disabled by the user").
- The doctor is core in all three that have one (`cloud-init status/schema`, `brew doctor`, and HM's eval-time typing), and Homebrew explicitly frames doctor warnings as non-blocking triage aids.
- The "too magical" complaints cluster around defaults that act without being asked (Homebrew auto-update/analytics, cloud-init first-boot-only semantics, HM read-only symlinks); every project answered with an env-var/option opt-out plus better observability, not by removing the default.
