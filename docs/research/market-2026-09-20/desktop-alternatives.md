# Desktop and VM alternatives: evidence notes

Research snapshot: 20 September 2026. This is desk research of official repositories, documentation, release notes and issue reports, not hands-on testing. User reports establish that a person encountered a problem; they do not establish its frequency. Closed issues are historical friction, not claims that the bug remains unfixed. Repository statistics below were read through GitHub's API during this research and measure attention, not active installations.

## Assessment

The broad idea already exists in several useful forms. Cua is substantially ahead as a general computer-use infrastructure project. ClodPod closely matches the personal persistent macOS agent-machine use case. Code on Incus already serves Linux users wanting native coding agents, persistent environments, root, Docker, profiles and parallel isolation. Bytebot previously packaged an agent with a persistent Linux desktop, and LinuxServer's Webtop/Pelorus stack currently demonstrates that desktop containers are technically credible.

No evidence examined here establishes a universally better, polished, free tool that delivers all of: the user's chosen native agent application, a persistent authenticated desktop, Linux-host-first operation, strong host/LAN policy, uncomplicated human access, several machines, and Linux/Windows/macOS guests. However, almost every ingredient exists, and Cua/Lima are moving into broader coverage. The opportunity would be reliable integration and good defaults for a specific workflow, not novel virtualization.

The strongest positioning to test is **a personal computer for an agent, on hardware you own, with a visible and understandable boundary**. This is an inference from the user requests below. It is not validated demand for a large cross-platform orchestration product.

### Cua's local support deserves precise wording

[Current runtime documentation](https://cua.ai/docs/reference/sandbox-sdk/runtime-support) explicitly distinguishes SDK selection from proof that a guest boots. It maps Linux VM to bare-metal QEMU, Linux container to Docker, macOS to Lume on compatible Apple Silicon, and Windows to Hyper-V/QEMU paths. Windows 11 requires suitable local installation media. Avoid copying older all-green support matrices as proof of every host/guest combination.

[Local lifecycle documentation](https://cua.ai/docs/how-to-guides/sandbox/manage-local-lifecycle) supports a persistent named `Sandbox.create`, disconnect without destruction and later reconnect. It is therefore inaccurate to dismiss Cua as ephemeral-only or cloud-only. The docs are operation patterns rather than a complete ready-to-use native-agent desktop installer. That remaining packaging distinction could matter, but it is thinner than an entirely missing capability.

[Lume's installation page](https://cua.ai/docs/how-to-guides/lume/install-lume) documents local macOS/Linux VMs on Apple Silicon. It does not establish Windows guest support or Linux hosts for Lume itself. Cua's broader project has other runtimes.

### Lima now covers more than Linux

[Lima macOS guest documentation](https://lima-vm.io/docs/usage/guests/macos/) says macOS guests are experimental since v2.1 and require an ARM Mac with a host OS at least as new as the guest. Automatic port forwarding and custom CA installation are not supported there. [Windows guests](https://lima-vm.io/docs/usage/guests/windows/) are experimental since v2.2 and use QEMU; Windows 11 ISO acquisition is manual, only plain mode is supported, file mounting/dynamic forwarding are absent, and occasional boot failures are documented. The [Windows 11 template](https://github.com/lima-vm/lima/blob/master/templates/windows-11.yaml) has both x86_64 and ARM64 entries.

[Lima v2.2 release notes](https://github.com/lima-vm/lima/releases/tag/v2.2.0) date the Windows guest release to July 2026. Consequently, a future Mac mini fleet should assess Lima as a candidate common backend before assuming three entirely separate implementations. This is an engineering hypothesis; support is experimental, and it does not provide the finished agent desktop experience. [Lima explicitly documents running native agent CLIs inside VMs](https://lima-vm.io/docs/config/ai/inside/).

### General virtualization is a substitute too

[Quickemu](https://github.com/quickemu-project/quickemu/blob/master/README.md) already wraps QEMU to automate guest acquisition/configuration for many operating systems, supports Linux/macOS hosts, ARM guests and desktop integration. [UTM's Windows guide](https://docs.getutm.app/guides/windows/) documents Windows guests on Mac. A capable user can install agents into these machines manually. These tools weaken the novelty argument but do not remove value from repeatable provisioning, tested boundaries, guest setup, access and recovery.

Tart's [current repository license](https://github.com/openai/tart/blob/main/LICENSE) is FSL-1.1-ALv2, with an Apache-2.0 future-license provision. The original repository redirects to `openai/tart`. The separate [tart.run licensing page](https://tart.run/licensing/) still presents Fair Source tiers; it should not override the checked repository license. Do not label the entire ClodPod/Chamber dependency stack permissively open-source solely because the wrapper is Apache/AGPL. This is a source observation, not legal advice.

## What this suggests building, and what it does not

The reviewed evidence supports investment in repeatable first-run setup, persistent agent/browser identity, clone/reset workflows, clear network boundaries, easy human desktop access, and reliable multi-instance behavior. The GUI/session and VPN failures make the mundane integration work look important. A thin wrapper can be useful if it is the place those details are solved and kept working.

It does not support competing broadly with Cua on SDKs, every OS, custom computer-use drivers, hosted fleets, model integration and benchmarks. Nor does it support assuming that people asking for a desktop sandbox also want a new agent UI or agent framework. Native applications and existing subscriptions are a separate preference from bringing a model API key to Bytebot/Coasty/custom SDK code.

“Containers do not work for GUI” would be an unsound differentiator. Bytebot, AgentDesk and Webtop establish otherwise. A better distinction is the full guest OS, separate kernel, unrestricted administration inside that guest, and the workflow around long-lived state. BoxLite also establishes that a microVM can expose a desktop. The choice should follow application compatibility and operational needs rather than a categorical full-VM-versus-container argument.

OpenCUA is worth tracking as an upstream capability, not treating as a close replacement: its [official repository](https://github.com/xlang-ai/OpenCUA) is primarily models, datasets, demonstration collection and evaluation infrastructure. It does not package the personal VM ownership workflow described here.

A network policy component may be integrated rather than reinvented. [Trollbridge](https://trollbridge.dev/) documents an Incus VM with the proxy on the host and firewall-enforced proxy-only egress. It provides HTTP policy and approval/audit functions, not the VM or desktop lifecycle. This review did not verify its security guarantees.

The most credible next validation is to give a narrowly supported desktop setup to several real users and observe whether they still use it after the initial novelty: do they return to the same machine, keep authenticated sessions, clone it, and prefer it to ClodPod/Cua or plain VM instructions? The public evidence warrants that experiment. It does not yet warrant a large modular cross-platform platform build.
