# Core / default / packs: how comparable tools draw the lines, and what that suggests for yolovm

Research date: 2026-09-19. Method: five parallel primary-source sweeps (official docs, repos, release notes, issue trackers) plus direct re-verification of the load-bearing claims (Docker Sandboxes kit contract and network presets, Omarchy 4.0 plugin manifest, Incus profile/ACL/cloud-init semantics, and the login/doctor commands of `gh`, Claude Code and Codex). Every factual claim links its source; anything that could not be confirmed is marked "unverified". Nothing under `/home/tochkov/PROJ` was touched.

## 1. Executive summary: what the survivors have in common

1. **Every tool that stayed usable has both an explicit bare switch and an opinionated default.** Lima `--plain` vs `default.yaml` ([plain](https://lima-vm.io/docs/config/plain/)); `ansible-core` vs the `ansible` bundle ([release page](https://docs.ansible.com/ansible/latest/reference_appendices/release_and_maintenance.html)); k3s bundles Traefik/ServiceLB/CoreDNS but `--disable` removes any of them ([packaged components](https://docs.k3s.io/installation/packaged-components)); Omarchy ships "Remove > Preinstalls" ([FAQ](https://omarchy.org/manual/faq/)). Counter-examples: Vagrant has no default box, so first run is homework ([machine settings](https://developer.hashicorp.com/vagrant/docs/vagrantfile/machine_settings)); the Dev Container spec defines no default image, so Codespaces had to invent the "universal" image ([Codespaces](https://docs.github.com/en/codespaces/setting-up-your-project-for-codespaces/adding-a-dev-container-configuration/introduction-to-dev-containers)).
2. **Curated catalogs decay; fetchable units survive.** Multipass Blueprints went 2021 → deprecated 2025 with the advice "You can achieve similar effects with cloud-init" ([blueprint doc](https://canonical.com/multipass/docs/stable/explanation/blueprint/)); Lima keeps a "Lost+found" of removed templates ([templates](https://lima-vm.io/docs/templates/)); Omakub's `EXTENSIONS.md` lists one community extension ([EXTENSIONS.md](https://github.com/basecamp/omakub/blob/master/EXTENSIONS.md)). What survives is a directory plus a two-field manifest anyone can host: Dev Container Features replaced the in-repo script library because it "lacked independent publishing, versioning and customization" ([VS Code blog](https://code.visualstudio.com/blogs/2022/09/15/dev-container-features)).
3. **The extension unit converges on: directory + small manifest + install script + options with defaults + a "once at create" vs "every start" split.** sbx kits: `setup.install` (once) vs `setup.startup` ("must be idempotent") ([kits](https://docs.docker.com/ai/sandboxes/customize/kits/)); Colima `provision` modes `system|user|after-boot|ready` ([colima.yaml](https://raw.githubusercontent.com/abiosoft/colima/main/embedded/defaults/colima.yaml)); cloud-init module frequency `per-instance|always|once` ([modules](https://docs.cloud-init.io/en/latest/reference/modules.html)); Vagrant `run: once|always|never` ([provisioning](https://developer.hashicorp.com/vagrant/docs/provisioning/basic_usage)).
4. **Almost nobody has a "check" hook, and nobody but sbx and Coder models credentials.** Checks exist as Multipass `health-check`, Lima readiness `probes`, Homebrew `test do`, sbx `kit validate` + a TCK ([sbx-kits-contrib](https://github.com/docker/sbx-kits-contrib)). Login is first-class only in sbx (`sbx secret set`, credentials "never enter the VM" ([security](https://docs.docker.com/ai/sandboxes/security/))) and Coder's claude-code module (seven auth methods, [README](https://raw.githubusercontent.com/coder/registry/main/registry/coder/modules/claude-code/README.md)). This is open space yolovm can own: an install + configure + login + check unit is not something users already have.
5. **Overrides work by layered priority and ownership-by-directory, never by "don't touch".** Omarchy: `/usr/share/omarchy` is theirs, `~/.config` is yours, and `hyprland.lua` "Loads the Omarchy defaults plus your override files" ([dotfiles](https://omarchy.org/manual/dotfiles/)); oh-my-zsh `custom/` "will take precedence over the built-in configuration" ([customization](https://github.com/ohmyzsh/ohmyzsh/wiki/Customization)); Lima `_config/default.yaml < lima.yaml < override.yaml` ([default.yaml](https://raw.githubusercontent.com/lima-vm/lima/master/templates/default.yaml)); cloud-init user-data over vendor-data ([vendordata](https://docs.cloud-init.io/en/latest/explanation/vendordata.html)); Incus profiles in order, "instance-specific configuration always overrides" ([profiles](https://linuxcontainers.org/incus/docs/main/profiles/)).
6. **Every long-lived default grew an uninstall.** Omakub added uninstallers release by release and moved apps to optional (Tailscale, Discord, GIMP) ([releases](https://github.com/basecamp/omakub/releases)); casks have `uninstall` and `zap` ([cask cookbook](https://docs.brew.sh/Cask-Cookbook)); `brew bundle cleanup` removes what the Brewfile no longer lists ([manpage](https://docs.brew.sh/Manpage)).
7. **The doctor is always core, non-blocking, and composed of per-unit checks.** `brew doctor` exits non-zero on any potential problem yet says "just ignore this" if things work ([manpage](https://docs.brew.sh/Manpage)); `cloud-init status` exits 0/1/2 and `schema --annotate` explains YAML ([cli](https://docs.cloud-init.io/en/latest/reference/cli.html)); `claude doctor` prints "install health, settings-file validation errors, and Remote Control eligibility" ([cli reference](https://code.claude.com/docs/en/cli-reference)); `gh auth status` and `claude auth status` exit 1 when not logged in ([gh](https://cli.github.com/manual/gh_auth_status)), so pack checks can wrap vendor checks.
8. **"Too magical" complaints cluster on defaults that act unasked, and the fix was never fewer opinions.** Homebrew auto-update and analytics ([#9285](https://github.com/Homebrew/brew/issues/9285), [#142](https://github.com/Homebrew/brew/issues/142)) got env-var opt-outs and a cheaper update, not removal ([4.0.0](https://brew.sh/2023/02/16/homebrew-4.0.0/)); sbx renamed `docker sandbox` to `sbx` and dropped snapshots "without any notice, any migration steps" ([forum](https://forums.docker.com/t/docker-sandbox-completely-changed-in-a-minor-update/151458)). Inspectors matter: Compose has `docker compose config`; sbx users are asking for `sbx kit inspect --resolved` ([#606](https://github.com/docker/sbx-releases/issues/606)).
9. **Security defaults draw the loudest fire, and the respected answer is a written trade-off.** Omarchy's docker-group root escalation ([0xcc](https://0xcc.io/posts/omarchy-root-creds/)) and `curl | sh` critiques ([a word on omarchy](https://xn--gckvb8fzb.com/a-word-on-omarchy/)) versus its security page stating that with passwordless sudo "anything running as your user can do anything as root without being asked" ([security](https://omarchy.org/manual/security/)). sbx's stance: "The sandbox itself is the safety boundary", so YOLO mode is the default ([FAQ](https://docs.docker.com/ai/sandboxes/faq/)).
10. **The agent-tooling crowd already has a mental model of an extension:** a git directory with `plugin.json`/`SKILL.md`, a `marketplace.json` in a repo, `<tool> plugin add <url|name@marketplace>`, `${PLUGIN_ROOT}`, `hooks.json`, per-scope enable ([Claude plugins reference](https://code.claude.com/docs/en/plugins-reference), [Codex plugins](https://learn.chatgpt.com/docs/plugins), [Gemini extensions](https://github.com/google-gemini/gemini-cli/blob/main/docs/extensions/reference.md), [Agent Plugins 1.0](https://agent-plugins.org/specification)). yolovm's unit should rhyme with that but must not be called "plugin", because to these users a plugin is something that runs *inside the agent*.

## 2. Per-tool findings (condensed)

Each card: **Core** · **Default** · **Unit and interface** · **Distribution** · **Override** · **Lessons**.

### 2.1 VM managers

**Lima.** Core: `limactl` + drivers (qemu/vz/wsl2) + a gRPC driver API; `--plain` strips mounts, port forwarding, containerd and the guest agent ([plain](https://lima-vm.io/docs/config/plain/)). Default: `limactl start` with no args creates instance `default` from the Ubuntu template, prompting in a TTY (proceed / edit / pick another template / exit; `--tty=false` for scripts) ([start](https://lima-vm.io/docs/reference/limactl_start/), [usage](https://lima-vm.io/docs/usage/)); `default.yaml` = 4 CPUs, 4 GiB, 100 GiB, read-only home, user-mode containerd ([default.yaml](https://raw.githubusercontent.com/lima-vm/lima/master/templates/default.yaml)). Unit: template YAML with `provision:` modes `system|user|boot|dependency|data|yq` and readiness `probes:`; `base:` composition merges lists and maps ([PR #3072](https://github.com/lima-vm/lima/pull/3072)); v2.0 added PATH plugins `limactl-<cmd>` and URL handlers `limactl-url-<scheme>` ([cli plugins](https://lima-vm.io/docs/config/plugin/cli/), [url](https://lima-vm.io/docs/config/plugin/url/), [v2.0.0](https://github.com/lima-vm/lima/releases/tag/v2.0.0)). Distribution: in-repo `templates/` (~65 files, ⭐ = CI-tested) as `template:NAME`, or any file/URL ([templates](https://lima-vm.io/docs/templates/)). Override: `~/.lima/_config/default.yaml` < instance `lima.yaml` < `override.yaml`, plus `--set` yq expressions ([default.yaml](https://raw.githubusercontent.com/lima-vm/lima/master/templates/default.yaml)). Lessons: read-only home is the standing "surprising default", kept with a one-flag escape ([#1872](https://github.com/lima-vm/lima/issues/1872)); v1.0 folded experimental templates into flags and printed hints on breaking changes ([v1.0.0](https://github.com/lima-vm/lima/releases/tag/v1.0.0)); Colima, Finch and Rancher Desktop exist because Lima is a VM tool, not a container product ([#1349](https://github.com/abiosoft/colima/discussions/1349)).

**Colima.** Core: "Containers on Lima", Ubuntu-only image, runtimes docker (default) | containerd | incus | none ([README](https://raw.githubusercontent.com/abiosoft/colima/main/README.md), [FAQ](https://raw.githubusercontent.com/abiosoft/colima/main/docs/FAQ.md)). Default: `colima start` = Docker, 2 CPU / 2 GiB / 100 GiB, docker context auto-activated, writable home, automatic port forwarding ([README](https://raw.githubusercontent.com/abiosoft/colima/main/README.md), [colima.yaml](https://raw.githubusercontent.com/abiosoft/colima/main/embedded/defaults/colima.yaml)). Unit: no plugin system; `provision:` entries "executed on startup and therefore needs to be idempotent" with modes `system|user|after-boot|ready`; raw-Lima escape via `_lima/_config/override.yaml` ([colima.yaml](https://raw.githubusercontent.com/abiosoft/colima/main/embedded/defaults/colima.yaml), [FAQ](https://raw.githubusercontent.com/abiosoft/colima/main/docs/FAQ.md)). Override: flags, `colima start --edit`, profiles; VM type/runtime/mount type are immutable after creation ([v0.7.0](https://api.github.com/repos/abiosoft/colima/releases/tags/v0.7.0)). Lessons: what it fixed was the *product* layer (socket, context, forwarding, k3s flag); what hurt was upgrade breakage requiring `colima delete` ([v0.6.0](https://api.github.com/repos/abiosoft/colima/releases/tags/v0.6.0)) and 9p mount performance ([#544](https://github.com/abiosoft/colima/issues/544)); users reward it as "one command that never needed cursing at" ([HN](https://news.ycombinator.com/item?id=36669121)).

**Multipass.** Core: Ubuntu VM manager on KVM/Hyper-V/QEMU with a root daemon ([README](https://raw.githubusercontent.com/canonical/multipass/main/README.md)). Default: `multipass launch` = latest LTS, 1 CPU / 1 GiB / 5 GiB, random name, `--cloud-init` file/URL/stdin ([launch](https://canonical.com/multipass/docs//en/latest/reference/command-line-interface/launch/)). Unit: Blueprint YAML (`description`, `version`, `runs-on`, `image`, `limits`, `cloud-init.vendor-data`, `health-check`) — i.e. image → cloud-init → check, no login ([blueprints README](https://raw.githubusercontent.com/canonical/multipass-blueprints/main/README.md), [docker.yaml](https://raw.githubusercontent.com/canonical/multipass-blueprints/main/v1/docker.yaml)). Distribution: one curated GitHub repo fetched by the daemon. Lessons: deprecated in 1.16.0 (July 2025) in favour of plain cloud-init files passed by URL ([1.16.0](https://api.github.com/repos/canonical/multipass/releases/tags/v1.16.0), [charm tutorial swap](https://github.com/canonical/mysql-operators/pull/508)); a pinned-image catalog with per-arch lists is a maintenance liability.

**Vagrant.** Core: Ruby `Vagrantfile`, boxes, providers, provisioners, and a plugin API the core itself dogfoods ([plugins](https://developer.hashicorp.com/vagrant/docs/plugins)). Default: none — `config.vm.box` has no default ([machine settings](https://developer.hashicorp.com/vagrant/docs/vagrantfile/machine_settings)). Unit: a RubyGem adding commands, providers, provisioners or guest/host capabilities; provisioners run `once|always|never` ([basics](https://developer.hashicorp.com/vagrant/docs/plugins/development-basics), [provisioning](https://developer.hashicorp.com/vagrant/docs/provisioning/basic_usage)). Distribution: RubyGems via `vagrant plugin install`; the HCP box registry ends operations December 31, 2026 ([EOL](https://developer.hashicorp.com/hcp/docs/vagrant/hcp-vagrant-eol)). Override: box Vagrantfile < `~/.vagrant.d/Vagrantfile` < project ([vagrantfile](https://developer.hashicorp.com/vagrant/docs/vagrantfile)). Lessons: BUSL got it dropped from Debian/Ubuntu ([launchpad](https://bugs.launchpad.net/bugs/2054608)); the Go rewrite was abandoned ([PR #13622](https://github.com/hashicorp/vagrant/pull/13622)); interpreter-bound plugins broke on upgrades, hence `plugin repair`/`expunge` ([cli](https://developer.hashicorp.com/vagrant/docs/cli/plugin)).

### 2.2 Agent sandboxes and containers

**Docker Sandboxes (`sbx`).** The closest analogue. Core (fixed, host-enforced): microVM with its own kernel and Docker daemon; host-side forward proxy that carries all outbound TCP, enforces policy and injects credentials; workspace passthrough at the same path; UDP/ICMP blocked, outbound deny-by-default ([architecture](https://docs.docker.com/ai/sandboxes/architecture/), [security](https://docs.docker.com/ai/sandboxes/security/)). Default: `sbx run --name my-sandbox claude` in a project dir; first run offers three named presets — "Open — All network traffic allowed", "Balanced — Default deny, with common dev sites allowed" (recommended), "Locked Down — All network traffic blocked unless you allow it" ([get started](https://docs.docker.com/ai/sandboxes/get-started/)); Claude runs as `claude --dangerously-skip-permissions`, `~/.claude` is deliberately not synced in ([claude-code](https://docs.docker.com/ai/sandboxes/agents/claude-code/)); "YOLO mode by default" ([sbx-releases](https://github.com/docker/sbx-releases)). Unit: **templates** (OCI images the VM boots from) and **kits** (`spec.yaml`, `kind: mixin|sandbox`, fields `name`, `extends`, `permissions.network.allow/deny`, `credentials`, `environment`, `setup.install` once at creation, `setup.startup` idempotent per start, `agentInstructions`, `sandbox.image`; run with root privileges; `sbx kit validate|inspect|pack|push|pull|sign|verify`) ([customize](https://docs.docker.com/ai/sandboxes/customize/), [kits](https://docs.docker.com/ai/sandboxes/customize/kits/)). Distribution: local path/zip, `git+https://…#ref=`, OCI; by default "Only kits hosted on Docker Hub are allowed" (`kit.allowedSources`) ([kits](https://docs.docker.com/ai/sandboxes/customize/kits/)); contrib kits auto-publish as `docker.io/sbx/<kit>-kit` with signed commits and a TCK ([sbx-kits-contrib](https://github.com/docker/sbx-kits-contrib)). Login: `sbx secret set anthropic|openai|github…`, `--command 'gh auth token'`, OAuth stays on host ([credentials](https://docs.docker.com/ai/sandboxes/configuration/credentials/)). Lessons: the CLI rename and lost snapshot feature angered users ([forum](https://forums.docker.com/t/docker-sandbox-completely-changed-in-a-minor-update/151458)); Balanced was too narrow for doc sites yet Docker warns its wildcards are broad ([Andrew Lock](https://andrewlock.net/running-ai-agents-safely-in-a-microvm-using-docker-sandbox/), [security](https://docs.docker.com/ai/sandboxes/security/)); layering template + kit + policy is opaque ([#606](https://github.com/docker/sbx-releases/issues/606)); agents ship only as whole sandbox kits, so mixing harnesses means reverse-engineering ([#594](https://github.com/docker/sbx-releases/issues/594)).

**Dev Containers.** Core: `devcontainer.json` (`image` | `build` | `dockerComposeFile`), lifecycle `initializeCommand → onCreateCommand → updateContentCommand → postCreateCommand → postStartCommand → postAttachCommand` ([json reference](https://containers.dev/implementors/json_reference/)); reference CLI with `features test|package|publish`, `templates apply|publish`, lockfile ([cli](https://github.com/devcontainers/cli)). Default: no default image in the spec; the opinionated base `mcr.microsoft.com/devcontainers/base:ubuntu` = git, zsh, Oh My Zsh, non-root `vscode` with sudo, built from the `common-utils` Feature ([base-ubuntu](https://github.com/devcontainers/images/blob/main/src/base-ubuntu/README.md), [common-utils](https://github.com/devcontainers/features/blob/main/src/common-utils/README.md)). Unit: **Feature** = `devcontainer-feature.json` (`id`, `version`, `name`, `options` with `default`/`enum`/`proposals`, `containerEnv`, `dependsOn`, `installsAfter`, `customizations`, lifecycle hooks) + `install.sh` run as root at build with options uppercased as env vars ([features](https://containers.dev/implementors/features/)); **Template** = `devcontainer-template.json` + `.devcontainer.json` with `${templateOption:x}` ([templates](https://containers.dev/implementors/templates/)). Distribution: OCI (`ghcr.io/ns/id:1`), tgz URL, or local; a crawled `collection-index.yml` lists >350 collections ([distribution](https://containers.dev/implementors/features-distribution/), [collections](https://containers.dev/collections)). Lessons: Features won because they were independently publishable and versioned ([VS Code blog](https://code.visualstudio.com/blogs/2022/09/15/dev-container-features)); perf (one layer per Feature, no build cache) is the perennial complaint ([spec #21](https://github.com/devcontainers/spec/issues/21)); Claude Code calls a dev container "a convention rather than an enforcement boundary" ([sandbox-environments](https://code.claude.com/docs/en/sandbox-environments)).

**Docker Compose.** Core: `compose.yaml` (legacy names accepted, `version` ignored) ([model](https://docs.docker.com/compose/intro/compose-application-model/)). Default: `docker compose up` merges `compose.override.yaml` automatically; unprofiled services always start ([merge](https://docs.docker.com/compose/how-tos/multiple-compose-files/merge/), [profiles](https://docs.docker.com/compose/how-tos/profiles/)). Unit: `extends`, `include:` (each file "loaded as an individual Compose application model", `oci://` sources), `profiles:`, `x-` fields ([include](https://docs.docker.com/reference/compose-file/include/), [extension](https://docs.docker.com/reference/compose-file/extension/)). Override: documented merge rules with `!reset`/`!override` ([merge rules](https://docs.docker.com/reference/compose-file/merge/)). Lessons: appended ports surprise people ([akrabat](https://akrabat.com/changing-port-maps-in-docker-compose/)); the v2/v3 split was undone by the spec ([history](https://docs.docker.com/compose/intro/history/)); `docker compose config` as the resolved-view inspector is what makes layering survivable.

**Coder.** Core: workspaces from Terraform templates; Template Admin vs Member roles; user-side `coder dotfiles` ([templates](https://coder.com/docs/admin/templates), [roles](https://coder.com/docs/admin/users/groups-roles), [dotfiles](https://coder.com/docs/user-guides/workspace-dotfiles)). Default: a template builder plus `coder templates init` starters (docker, kubernetes, incus, quickstart, scratch…) ([init](https://coder.com/docs/reference/cli/templates_init)). Unit: **module** = `main.tf` + README frontmatter + tests, referenced as `source = "registry.coder.com/coder/<name>/coder"`; the claude-code module supports seven auth methods and hit v5 with a breaking refactor ([CONTRIBUTING](https://github.com/coder/registry/blob/main/CONTRIBUTING.md), [claude-code](https://raw.githubusercontent.com/coder/registry/main/registry/coder/modules/claude-code/README.md)). Lessons: modules were extracted because templates "had grown to include IDE installs, auth and tool integration with duplicated code" ([registry blog](https://coder.com/blog/introducing-the-coder-registry)); Terraform is the entry tax ([operator write-up](https://thetechenabler.substack.com/p/running-a-vibe-code-platform-coder)); a hijacked registry served secret-exfiltrating modules (CVSS 9.0) and lockfiles pin providers, not modules ([advisory](https://github.com/coder/coder/security/advisories/GHSA-vx42-ghc9-gw65)); Coder then moved agent loops into the control plane so "LLM provider credentials never enter the workspace" ([Coder Agents](https://coder.com/blog/introducing-coder-agents)).

**Anthropic sandbox-runtime (`srt`).** OS-level sandbox (bubblewrap + seccomp on Linux, Seatbelt on macOS) with proxy-based network filtering; config `~/.srt-settings.json` with `allowedDomains`/`deniedDomains`/`allowLocalBinding` and `allowWrite`/`denyWrite`/`denyRead`/`allowRead`; with no config: "no network access, no writes outside the default write paths, and unrestricted reads" ([repo](https://github.com/anthropic-experimental/sandbox-runtime)). Lesson: policy is a small allow/deny document with a secure default, not a menu of modes.

### 2.3 Configuration management and package managers

**cloud-init.** Core: five boot stages; datasource abstraction ("users of cloud-init should not have to configure cloud-init to specify which datasource"); NoCloud reads `user-data`/`meta-data`/`vendor-data` from a `CIDATA` volume; doctor surface `status` (exit 0/1/2, `--wait`), `schema --annotate`, `analyze`, `collect-logs`, `clean` ([boot](https://docs.cloud-init.io/en/latest/explanation/boot.html), [datasources](https://docs.cloud-init.io/en/latest/reference/datasources.html), [cli](https://docs.cloud-init.io/en/latest/reference/cli.html)). Default: shipped `cloud.cfg` runs a long module list, most of which are no-ops without their key ([cloud.cfg.tmpl](https://raw.githubusercontent.com/canonical/cloud-init/main/config/cloud.cfg.tmpl), [modules](https://docs.cloud-init.io/en/latest/reference/modules.html)). Unit: user-data parts (`#cloud-config`, `#!`, `#include`, MIME) for users; in-tree `cc_<name>.py` with `meta.frequency` for implementers; out-of-tree modules allowed but unmaintained ([format](https://docs.cloud-init.io/en/latest/explanation/format.html), [module creation](https://docs.cloud-init.io/en/latest/development/module_creation.html)). Override: user-data over vendor-data; vendors must keep vendor-data "safe, atomic, idempotent" and "If the use of vendor-data is required for the instance to run, then vendor-data should not be used" ([vendordata](https://docs.cloud-init.io/en/latest/explanation/vendordata.html)). Lessons: first-boot-only semantics and pre-SSH failures are the top gotchas; re-run needs `cloud-init clean --logs --reboot` ([rerun](https://docs.cloud-init.io/en/latest/howto/rerun_cloud_init.html)); the project answered with more doctor, not fewer modules ([debugging](https://docs.cloud-init.io/en/latest/howto/debugging.html)). Incus passes `cloud-init.user-data`/`vendor-data`/`network-config` via profiles or instances, only `/cloud` images run it, and "only once on the first start" ([Incus cloud-init](https://linuxcontainers.org/incus/docs/main/cloud-init/)).

**Ansible.** Core: since 2.10, `ansible-core` (engine + `ansible.builtin`, 93 modules) vs the `ansible` package bundling ~104 collections; the split was made "to remove the Core maintainers as a bottleneck to community module and plugin development" ([porting 2.10](https://docs.ansible.com/ansible/latest/porting_guides/porting_guide_2.10.html), [builtin](https://docs.ansible.com/ansible/latest/collections/ansible/builtin/index.html), [deps](https://raw.githubusercontent.com/ansible-community/ansible-build-data/main/12/ansible-12.0.0.deps), [Doran](https://groups.google.com/g/ansible-devel/c/oKqgCeYTs-M/m/cHrOgMw8CAAJ)). Unit: **role** = `tasks/ handlers/ defaults/ vars/ files/ templates/ meta/`; `defaults/main.yml` is the tunable surface (geerlingguy.docker exposes ~20 variables and nothing else), `meta/main.yml` carries dependencies and platforms, `argument_specs.yml` validates inputs ([roles](https://docs.ansible.com/ansible/latest/playbook_guide/playbooks_reuse_roles.html), [docker defaults](https://raw.githubusercontent.com/geerlingguy/ansible-role-docker/master/defaults/main.yml)); **collection** = `galaxy.yml` (`namespace`, `name`, `version`, `dependencies`) + `plugins/ roles/ playbooks/` ([galaxy.yml](https://docs.ansible.com/ansible/latest/dev_guide/collections_galaxy_meta.html)). Distribution: `requirements.yml` pulls from Galaxy or `git+https://…` with tag/commit ([user guide](https://docs.ansible.com/ansible/latest/galaxy/user_guide.html)). Override: 22-level precedence, role defaults near the bottom, extra vars "always win" ([variables](https://docs.ansible.com/ansible/latest/playbook_guide/playbooks_variables.html)). Lessons: bloat debates continue (a 26 MB collection; "size does not become a metric, but general applicability") and formal removal criteria exist ([forum](https://forum.ansible.com/t/including-large-specialized-collections-in-ansible-community-package/46222), [removal](https://docs.ansible.com/ansible/latest/community/collection_contributors/collection_package_removal.html)); roles-vs-collections seams confuse ([forum](https://forum.ansible.com/t/specifying-collections-required-by-required-roles/37199)); the Galaxy-NG cutover broke role publishing ([Geerling](https://www.jeffgeerling.com/blog/2023/ansible-galaxy-error-unable-compare-role-versions/)).

**Homebrew.** Core: `brew` installs into kegs under a fixed per-platform prefix; `brew doctor` (~55 checks, two fatal) is core and explicitly non-blocking; `bundle` and `services` moved *into* core in 4.5.0 ([brew.sh](https://brew.sh/), [manpage](https://docs.brew.sh/Manpage), [diagnostic.rb](https://raw.githubusercontent.com/Homebrew/brew/HEAD/Library/Homebrew/diagnostic.rb), [4.5.0](https://brew.sh/2025/04/29/homebrew-4.5.0/)). **Nix home-manager.** Core: NixOS module system for `$HOME`; bare primitives `home.packages`, `home.file`, `home.stateVersion` (lets defaults evolve without breaking old users) ([intro](https://nix-community.github.io/home-manager/introduction.html), [stateVersion](https://mynixos.com/home-manager/option/home.stateVersion)). Lessons: "an extra layer on the already not-beginner-friendly Nix ecosystem" ([HN](https://news.ycombinator.com/item?id=37819217)); read-only symlinks fight tool-edited files ([#257](https://github.com/nix-community/home-manager/issues/257)); "install only" via `home.packages` is an officially valid use ([wiki](https://wiki.nixos.org/wiki/Home_Manager)).

### 2.6 The substrate: Incus

Incus already has the layering yolovm needs. Profiles: the `default` profile is applied when none is given and "cannot be renamed or removed"; multiple profiles apply in order, "the last profile to specify a specific key takes precedence", and "instance-specific configuration always overrides the configuration coming from the profiles" ([profiles](https://linuxcontainers.org/incus/docs/main/profiles/)). Network ACLs attach via `security.acls` on a network or NIC; "a default reject rule is added to the NIC", tunable with `security.acls.default.{ingress,egress}.action`; available on OVN and "the Bridge network (with some exceptions)", with `@internal`/`@external` OVN-only ([ACLs](https://linuxcontainers.org/incus/docs/main/howto/network_acls/)). cloud-init: vendor-data in profiles for general defaults, user-data per instance, first boot only ([cloud-init](https://linuxcontainers.org/incus/docs/main/cloud-init/)). Implication: yolovm's core tier can be expressed as Incus profiles (network + ACL + vendor-data) and per-VM choices as instance config, reusing Incus's own precedence instead of inventing one.

## 3. Three candidate ways to draw the lines for yolovm

### Option A — "Lima-shaped": bare core + a default template that composes packs

- **Core**: `yolovm` CLI (create/start/stop/shell/delete), Incus profiles carrying the isolation boundary (network ACL blocking host and LAN, VM-to-VM port isolation), cloud-init hand-off, the pack runner, and the doctor framework. `yolovm create --bare` (Lima's `--plain`) produces an Ubuntu VM with nothing but the boundary and the `ubuntu` user.
- **Default**: a data file, `templates/default.yaml` (or `desktop.yaml`), listing base image (desktop), policy values (passwordless sudo on, bypass-permissions on) and the packs to enable with their options. A second file `headless.yaml` is the same minus desktop-dependent packs. Templates compose like Lima `base:`.
- **Packs**: directories, in-repo for built-ins, `yolovm pack add <git-url>` for others.
- **First run**: `yolovm create` → "Creating VM `default` from template `desktop`" → boundary applied → packs install → interactive logins in sequence (`gh auth login`, `claude auth login`, `codex login --device-auth`, `tailscale up`) → `yolovm doctor` summary → `yolovm shell`/desktop opens.
- **Pros**: the default is data, so forks and roles are file edits, not code; "what is on by default" is answerable by opening one file; headless is a second template not a fork; matches the tool users already know (Lima/Colima, Multipass cloud-init).
- **Cons**: template composition semantics (merge order, list append vs replace) must be designed and documented — Lima `base:` and Compose `override` both generate "why did my ports append" surprises ([merge rules](https://docs.docker.com/reference/compose-file/merge/)); a template *catalog* is the thing that rots (Multipass); an interactive "which template?" prompt on no-arg create is a known automation papercut (Lima's `--tty=false`, [#1420](https://github.com/lima-vm/lima/discussions/1420)) — keep the no-arg path non-interactive.

### Option B — "sbx/Omarchy-shaped": one opinionated product with removable preinstalls

- **Core and default are the same shipped thing.** There is no separate template concept; the product is "the yolovm VM", and the built-in items are *preinstalls*. The bare tier is reachable only by subtraction: `yolovm create --without chatgpt,chrome` or `--bare` (k3s `--disable`, Omarchy "Remove > Preinstalls").
- **Packs**: only for extras beyond the product; built-ins are code, not packs.
- **First run**: `yolovm create` → one VM, everything on, logins prompted, doctor at the end. Same as A but with no template vocabulary in the docs at all.
- **Pros**: simplest story for the "I just want it to work" crowd; the maintainer runs exactly what ships; no composition semantics; sbx and Omarchy prove this shape scales (1.15M ISO downloads; sbx's three named presets) ([omarchy.org](https://omarchy.org/), [get started](https://docs.docker.com/ai/sandboxes/get-started/)).
- **Cons**: built-ins written as code rather than packs means vendor churn lands in core releases (the Ansible bottleneck argument; Coder's claude-code module at v5 with a breaking refactor); "bare" being a subtraction feels wrong for a product whose promise is the boundary; customization becomes forking (Omakub's 801 forks) unless there is an ownership-by-directory contract; headless still needs a switch.

### Option C — "mise/Homebrew-shaped": three concentric rings by ownership

- **Core** = mechanism the maintainer owns and CI tests on every release: VM lifecycle, boundary profiles, pack runner, doctor, migrations, instructions-file assembly.
- **Default** = a *bundle* file (Brewfile / `plugins=(git)` style), `bundles/desktop` and `bundles/headless`, listing packs and options. Built-in packs live in-repo and are ⭐ CI-tested (Lima's mark); they are still packs with the same interface as third-party ones.
- **Packs** = the outer ring: `yolovm pack add <git-url|path>` into `~/.config/yolovm/packs/<id>/`; not vetted, never blocked, never given a short name until promoted (mise's registry rule; Omarchy's approved-and-verified marketplace if a listing is ever wanted).
- **First run**: identical to A from the user's point of view (`yolovm create` uses `bundles/desktop`), with `--bundle headless` and `--bare` as the two documented alternatives and `--without <pack>` for subtraction.
- **Pros**: tiers align with *who maintains what*, which is what actually decays; the bundle file is the one-glance answer to "what is on by default" and the trivially forkable customization surface; vendor churn is isolated in packs on their own cadence; community packs need no registry to exist.
- **Cons**: three rings to explain (mitigated by never saying "ring" in the README: the user sees `create`, `--bare`, `--without`, `pack add`); promotion/demotion needs a written policy (Ansible's removal criteria, Lima Lost+found); slightly more machinery on day one than B.

### Recommendation

Ship **B's user experience on C's file layout**: one no-arg `yolovm create`, no template vocabulary in the quick-start, but every built-in item implemented as a pack listed in a bundle, with `--bare`, `--without` and `pack add` as the only three escape hatches. Keep A's idea of templates only as "bundles" (a bundle is a list, not a merge tree — no composition semantics). Add sbx's named policy presets only if network egress ever becomes user-tunable; today the boundary is fixed, which is a feature.

## 4. Criteria for what goes where, tested against today's items

**Criteria** (each is a question; the first "yes" decides):

1. **Guarantee test** → core. If this were missing or wrong, would the product's promise ("isolated VM, full freedom inside") be broken or would the doctor be unable to say so? (sbx: VM, proxy, policy, credential injection are fixed; kits are not.)
2. **Host-side test** → core. Does it run on the host or need host privileges (Incus profiles, ACLs, port isolation, tailnet policy checks)? Packs run only inside the guest.
3. **All-flavors test** → core. Would headless and desktop both need it? If only one flavor needs it, it is default-tier data, not core.
4. **Vendor-cadence test** → pack. Does it install or configure a specific vendor's product, or need a login? Then it rots on the vendor's schedule and must ship independently (Ansible split rationale; Coder module churn; Omakub moving Tailscale/Discord to optional).
5. **Daily-driver test** → default. Does the maintainer run it daily and can CI check it on every release? Only then may a pack be on by default (Lima ⭐, Homebrew core CI, Ansible package inclusion rules). A default item must have `remove` and `check` (Omakub lesson).
6. **Policy-vs-mechanism split**: mechanisms (toggle passwordless sudo, set a permission mode, add an instructions fragment) are core; the *values* (on/off) are default-tier data, documented on a security page (Omarchy).
7. **Secret test**: anything holding a credential lives in a pack with a `login` verb; core config never contains secrets.

**Applied:**

| Item | Tier | Reasoning |
|---|---|---|
| Incus profiles, network ACL (no host/LAN), VM-to-VM port isolation | **Core** | Guarantee + host-side. Expressed as Incus profiles/ACLs; the doctor proves reachability is blocked. |
| Tailscale | **Default pack `tailscale`** + **core doctor check** | Installing/logging in is vendor work in the guest (criterion 4). But "VMs cannot initiate tailnet connections" is part of the guarantee, lives in the tailnet policy (host-side, criterion 2) and the ACL fence covers only the tailnet, not LAN ([acls](https://tailscale.com/kb/1018/acls)) — so core owns the check ("tag present, policy denies `src: tag:yolovm`") and the doc; the pack owns install/`tailscale up`/`tailscale status`. Omakub eventually made Tailscale optional; here it is default-on because Remote Control and the desktop story depend on it. |
| GitHub sign-in (`gh`) | **Default pack `github`** | Vendor, login. `install` = gh; `login` = `gh auth login`; `check` = `gh auth status` (exit 1 when broken) ([gh](https://cli.github.com/manual/gh_auth_status)); credentials in-VM by product design. |
| Claude Code | **Default pack `claude-code`** | Vendor, login, fast cadence. `install` = `claude install stable`; `configure` = settings + permission mode; `login` = `claude auth login`; `check` = `claude doctor` + `claude auth status`; `update` = `claude update` ([cli reference](https://code.claude.com/docs/en/cli-reference)). |
| Remote Control at boot | **Option of the `claude-code` pack**, default on in the desktop bundle | It is a `claude remote-control` server-mode systemd user unit; depends on Claude login and claude.ai plan; `claude doctor` reports eligibility, so the pack's `check` can surface it. Not core: headless may not want it; a different agent would not have it. |
| ChatGPT desktop app | **Default pack `chatgpt-app`**, desktop bundle only | Vendor, `requires: desktop`; rots fastest of all; must have `remove`. |
| Chrome + Claude/ChatGPT extensions | **Default pack `chrome`** with `extensions:` option, desktop bundle only | Vendor + policy-managed extension IDs; `requires: desktop`. |
| Codex config (full access) | **Default pack `codex`** | Vendor, login. `configure` writes `config.toml` with `sandbox_mode = "danger-full-access"` and `approval_policy = "never"`; `login` = `codex login --device-auth`; `check` = `codex login status` ([config](https://learn.chatgpt.com/docs/config-file/config-reference), [auth](https://learn.chatgpt.com/docs/auth)). The `--yolo` docs say "only for externally hardened environments" — yolovm *is* that environment; say so in the security page. |
| Instructions file (AGENTS.md / CLAUDE.md) | **Core mechanism, default content, pack fragments** | The file is the product's voice ("you are in an isolated VM…") and both vendors now read `AGENTS.md` ([agents-md](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [changelog](https://code.claude.com/docs/en/changelog)); core assembles it (like sbx `agentInstructions.content` per kit); each pack may contribute a section; default bundle supplies the base text. |
| Passwordless sudo for `ubuntu` | **Core mechanism, default value = on** | All flavors need it for packs to install; the boundary justifies it ("The sandbox itself is the safety boundary"); Omarchy's security page shows how to state the trade-off; a `--no-passwordless-sudo` toggle is cheap to keep. |
| Bypass-permissions (Claude) / full access (Codex) | **Default-tier values set through pack options** | Vendor config, so implemented in packs; but it is the product's defining opinion, so the bundle sets it and the README says why; the packs must also work with it off (headless CI users). Note Claude refuses bypass under root unless in a recognized sandbox — the non-root `ubuntu` user avoids that ([permission modes](https://code.claude.com/docs/en/permission-modes)). |
| The desktop itself | **A base/flavor chosen by the bundle, not a pack** | It is the image/base layer packs depend on (Lima `_images`, sbx template image); packs declare `requires: desktop`; `bundles/headless` omits it. Core must support both, which is the only reason to keep flavor in core's vocabulary. |
| The doctor | **Core framework; each pack contributes checks** | Core checks: Incus present, VM up, ACL attached, host/LAN unreachable, VM-to-VM blocked, `cloud-init status` clean, sudo policy as configured, instructions file present; pack checks: installed / configured / logged in. Non-blocking warnings with fixes, `--json` for scripts, `-v` for detail (brew/flutter/cloud-init pattern). |

Net effect: core is small (lifecycle, profiles/ACLs, pack runner, doctor, instructions assembly, migrations); the default bundle is a list of seven packs plus three policy values; everything vendor-specific is a pack. That is exactly the split the survivors converged on.

## 5. The pack interface and its name

**Verbs** (what the research shows is needed, and where each has precedent):

- `install` — once at create, as root (sbx `setup.install`; Feature `install.sh`; Colima `system`).
- `configure` — idempotent, runs at every start and after `yolovm update` (sbx `setup.startup` "must be idempotent"; Colima `ready`; cloud-init `always`). Writes config the *user* then owns (Devbox `create_files`; Omarchy defaults-then-overrides).
- `login` — interactive or device-code, re-runnable, credentials only inside the VM. Nobody has this verb; sbx and Coder are the only ones that model credentials at all. This is yolovm's differentiator, so make it first-class.
- `check` — exit 0/1 plus one human line and a JSON object, composed into `yolovm doctor`; wrap vendor checks (`gh auth status`, `claude auth status`, `claude doctor`, `codex login status`, `tailscale status`).
- `update` — vendor update (`claude update`, apt), default implementation = re-run `install`.
- `remove` — uninstall and drop config; required for anything in the default bundle (Omakub; cask `uninstall`/`zap`; `brew bundle cleanup`).
- `instructions` — optional AGENTS.md fragment (sbx `agentInstructions`; Gemini `contextFileName`).

**Declarative metadata** (a small manifest, not code): `name`, `version`, `description`, `requires` (`desktop`, other packs — Feature `dependsOn`), `options` with defaults and types (Feature `options`; Ansible `defaults/main.yml`), `network` (domains the pack needs — sbx's "complete outbound network contract" — even if only documented today), `checks` (names, for `doctor --list-checks`), `maintainer` (home-manager requires one).

**Shape.** Today's roles are bash functions; the least-change, most-familiar shape is one directory per pack with a tiny manifest and a script exposing functions:

```
packs/claude-code/
  pack.yaml      # name, version, description, requires, options, network, checks
  pack.sh        # pack_install, pack_configure, pack_login, pack_check, pack_update, pack_remove
  AGENTS.md      # optional instructions fragment
  files/         # optional templates copied by configure
```

Functions in one file mirror oh-my-zsh (`<name>.plugin.zsh`), Omakub (`app-<name>.sh` + `uninstall/app-<name>.sh`), and Lima's CLI plugins (a description read from a comment). A YAML/JSON manifest mirrors every agent-tooling format users already know (`plugin.json`, `manifest.json`, `spec.yaml`, `devcontainer-feature.json`). Guest-side layout should follow Omarchy's ownership-by-directory: `/usr/share/yolovm/packs/` is managed, `~/.config/yolovm/` is the user's, and per-pack state markers (like Omarchy's `~/.local/state/omarchy/migrations/`) make `configure` re-runnable and `doctor` honest.

**Distribution.** In-repo `packs/` for built-ins (CI-tested, the only ones a bundle may reference by short name); `yolovm pack add <git-url|path>` for others, cloned to `~/.config/yolovm/packs/<id>/` with `enable|disable|update|remove` (Omarchy, Gemini, Claude all use exactly this verb set). No registry until the third-party count justifies one; a `marketplace.json`-style index in a git repo is the cheap, familiar step when it does (Claude/Codex pattern). Pin by commit/tag (Claude community marketplace pins SHAs; Coder's incident shows unpinned modules are an attack surface).

**Bundles.** A bundle is a flat list `packs: [tailscale, github, claude-code: {remote_control: true}, codex, chrome, chatgpt-app]` plus policy values; no merging, no inheritance. Two shipped bundles (`desktop`, `headless`); users copy one to `~/.config/yolovm/bundles/` to make their own (Brewfile / `plugins=(git)`).

**Name.** Avoid **plugin** (to this audience it means skills/MCP/hooks *inside* the agent: Claude, Codex, Gemini, Agent Plugins 1.0) and **skill** (taken by the agentskills.io standard). **Kit** is sbx's word; **feature** is devcontainers'; **module** is Coder/home-manager/cloud-init and connotes code; **blueprint** died with Multipass; **template** is Lima/Coder/sbx's word for the *base image*, which yolovm should keep for flavors if it uses it at all. **Pack** is unclaimed by every tool surveyed, reads naturally in `yolovm pack add`, "starter pack", "the default packs", and matches the "install + configure + sign in + check something" meaning better than any alternative. Recommended vocabulary: **pack** (unit), **bundle** (list of packs = flavor), **doctor** (the check aggregator, already the industry word), and the verbs `install / configure / login / check / update / remove`.
