# Comparable tools: implementation language and backend interface

Survey date: 2026-09-19. Purpose: inform the choice of host-CLI language for the yolovm rewrite (Incus backend now, pluggable backends later; guest provisioner stays bash).

Method: every row was checked against at least one primary source (GitHub API metadata, repo READMEs/source files, pkg.go.dev import lists, official docs or blog posts). Star counts, creation dates and "last push" are GitHub API values from 2026-09-19. quickemu line counts were measured today with `curl | wc -l`. Anything I could not confirm from a primary source is marked **unverified**. Note that GitHub's "language" field is the majority language of the repo, not necessarily of the CLI (monorepos noted where relevant).

## 1. Table

Legend for "backend interface": **CLI** = spawns another tool's binary and parses output; **API** = REST/gRPC/QMP over a socket, usually via an official client library; **lib** = links the hypervisor library/framework in-process.

## 2. Patterns

1. **Wrappers around another CLI are written in whatever the author already had, and it works at small scale**: Colima (Go -> `limactl`), Vagrant (Ruby -> `VBoxManage`), quickemu (bash -> `qemu-system`), ClodPod/Chamber (bash/Go -> `tart`), sandbox-claude/incus-claude (bash -> `incus`), vibebin/code-on-incus (Go -> `incus`), DevPod (Go -> provider shell commands). Bash dominates the one-person "run agent X in box Y" scripts; Go dominates the ones that grew a daemon, a TUI, or multi-instance state.
2. **The serious managers do not shell out; they use the backend's socket API through the official client library or link the framework**: Incus/LXD CLI (Go client over the Unix socket), Lima (QMP via go-qemu; Virtualization.framework via Code-Hex/vz), UTM (QMP + Virtualization.framework), kraft (own QMP client + firecracker-go-sdk), Coder (REST + gRPC provisioners), Multipass (gRPC between CLI and daemon). Incus specifically is designed for this: the CLI is a thin layer over `github.com/lxc/incus/client`, and `incus --debug` shows the calls to copy.
3. **When a project defines a pluggable backend, the plugin boundary is a subprocess speaking gRPC or a manifest of shell commands, not a shared library**: Lima v2 external drivers (gRPC, `driver.proto`), Vagrant 3.0 plugins (go-plugin/gRPC), DevPod providers (`provider.yaml` exec), Podman machine (per-provider stubbers wrapping vfkit/krunkit/qemu/wsl.exe). Go is the common host language for all of these.
4. **Single-binary tools (Go, Rust, Swift) win on installation**: every rationale that names a reason names distribution first. Vagrant: shipping its own Ruby was "a long-standing issue" for packagers. goose: "as a distributable tool, we're missing out on ... a standalone binary". Codex: "Node v22+ is required, which is frustrating or a blocker". Claude Code moved from npm to a native installer in Jan 2026 for the same reason. Crush ships to brew/apt/yum/winget/scoop/nix/pkg from one Go build.
5. **Rust is chosen for security-adjacent cores and embeddability** (Firecracker "built-in security and correctness", Codex "native security bindings", goose "libraries available to python and javascript", microsandbox/BoxLite/smolvm as embeddable microVM runtimes, nono as a kernel-sandbox CLI). Go is chosen for orchestration and daemons (Incus, LXD, Podman, Lima, Coder, DevPod, Daytona runners, e2b infra, gVisor's kernel for memory safety). Swift only appears when Apple's Virtualization.framework is the backend (UTM, Tart, Apple container, lume).
6. **Python tools gain the SDK/user story, not the CLI story**: virt-manager (libvirt-python), aider, Modal, cua/e2b/Daytona SDKs. Python shows up where the user writes code against the tool; it does not appear in any of the VM managers surveyed, and its install story (pipx/uv/aider-install) is what goose left behind.
7. **TypeScript is the language of the agent CLIs themselves** (Claude Code ~513k lines, Gemini CLI, opencode 208k stars, Cline, Copilot CLI, e2b CLI, `srt`), because the vendors' SDKs and TUIs live there -- and it is precisely the vendor that tried to ship a sandbox in it (OpenAI) that left for Rust, while Anthropic kept TS but escaped Node by shipping a native binary.
8. **Bash projects that succeed hit a wall around 3k lines**: quickemu's maintainers describe it directly ("around 3000 lines... maintaining and extending has become challenging"; "everything is done via string manipulation"), and the escape routes proposed were modularisation, moving data out of code, and a Rust rewrite (which now exists as a side project). yolovm at ~320 lines is an order of magnitude below that wall, but the isolation policy (ACLs, port isolation, Tailscale) is exactly the kind of state-carrying logic that becomes "string manipulation" in bash.
9. **Migrations go bash -> Rust (quickemu-rs), Python -> Rust (goose), TS -> Rust (Codex), Ruby -> Go (Vagrant, stalled), Go -> TS (opencode, for the AI SDK ecosystem)**. The only migration toward a GC'd scripting runtime was driven by wanting a specific SDK, not by the sandboxing/VM part.
10. **Community contributions in the agent-sandbox niche cluster in Go and Rust, with bash for the personal scripts**: of the self-hosted sandbox repos verified here, Go: vibebin, code-on-incus, Matchlock, Arrakis, cs-sandbox, Chamber, container-use, bubblewrap-ai; Rust: microsandbox, BoxLite, smolvm, nono, quickemu-rs; Bash: sandbox-claude, incus-claude, ClodPod, lima-devbox, ai-bwrap, bwrap-sandbox; TypeScript: srt, agent-sandbox (ezerfernandes); Swift: Tart, lume, Apple container. The highest-starred self-hosted ones are Rust (smolvm 6.1k, nono 4.1k, microsandbox 8.3k, BoxLite 2.3k) and Go (container-use 4.0k), i.e. the ones that ship as a library/binary rather than a script.
11. **Persistence is rare**: most agent sandboxes are ephemeral microVMs (Matchlock, Chamber, Docker sbx per session, cs-sandbox, Arrakis with snapshots). The persistent ones are the Incus/LXC-based projects (vibebin, code-on-incus, sandbox-claude) and Coder/DevPod-style workspaces -- yolovm's niche.
12. **Nobody documents "why this language" unless they changed it**. Lima, Colima, Multipass, Incus, Podman, UTM, DevPod, Coder, Daytona and e2b have no published rationale; the only explicit statements come from rewrites (Vagrant, goose, Codex, quickemu discussion) and from security cores (Firecracker, gVisor).
13. **Every Go project that talks to Incus/LXD does so through the CLI or the official Go client -- there is no third path**; a non-Go host CLI would have to reimplement the REST client (pylxd-style) or shell out, and the Incus docs (`incus --debug`, `incus query`) assume you will copy the Go client's calls.

## 3. Projects closest to yolovm (isolated, persistent VM/container per agent, on your own hardware)

| Project | Same idea as yolovm | What it does differently |
|---|---|---|
| **sandbox-claude** (pvillega, Bash, 51 stars) | Incus instances, host and LAN unreachable, egress restricted, per-instance credentials | System **containers**, not VMs; macOS via OrbStack VM; egress via iptables on `incusbr0` plus optional Squid SNI allowlist rather than Incus network ACLs; no desktop mode; no Tailscale; bash only. |
| **code-on-incus / coi** (Go) | Incus system containers, persistent sessions, multiple parallel "slots", nftables network modes, credentials isolated by default | Containers rather than VMs; Linux-only by design; threat-detection auto-pause; Go binary with curl installer. |
| **vibebin** (Go, 108 stars) | Persistent Incus/LXC boxes with agents preinstalled, SSH straight into each box, snapshots | Targets a remote VPS with a web UI, Caddy HTTPS and SSHPiper routing; hosting apps is a goal; containers not VMs; drives Incus via the `incus` CLI. |
| **Docker Sandboxes / sbx** (proprietary) | One microVM per agent session, project dir mounted, network access control, agent kits | Ephemeral per session, custom VMM, closed source, Docker-centric; macOS/Windows/Linux; no Incus. |
| **ClodPod** (Bash, 187 stars) + **Chamber** (Go) | Full VM per agent with project dirs mapped in; the author explicitly rejected containers | macOS VMs on Tart (Apple Silicon only); reverse SSH tunnels to host services instead of blocking the host; no ACL layer. |
| **lima-devbox** / Lima-based setups (Shell, 28 stars) | Linux VM on your machine for YOLO-mode agents | macOS focus; Lima's default file sharing and port forwarding are the opposite of yolovm's isolation stance; no policy layer. |
| **cs-sandbox** (Go, 4 stars) | Named Linux sandboxes over SSH with Claude Code/Codex/OpenCode preinstalled | Firecracker or rootless Podman backends (already "pluggable"); ephemeral-leaning; very new. |
| **Matchlock** (Go, 621 stars) | Agent in a microVM, network allowlist, secrets kept host-side | Ephemeral microVMs (Firecracker/Virtualization.framework) instead of persistent VMs; MITM secret injection; SDKs in Go/TS/Python. |
| **Arrakis** (Go, 878 stars, inactive since 2025-06) | Self-hosted Ubuntu sandboxes with REST API, port forwarding, snapshots | cloud-hypervisor microVMs; server/API product rather than a personal CLI. |
| **Coder / DevPod** (Go) | Persistent dev environments for "developers and their agents" | Multi-user control plane (Coder) or devcontainer-on-any-provider (DevPod, now dormant); far heavier than a local CLI; Terraform/devcontainer instead of a bash provisioner. |

Nothing found combines all of yolovm's ingredients (Incus **VMs** rather than containers, desktop or headless, Incus network ACLs blocking host and LAN, VM-to-VM port isolation, and a Tailscale policy) in one tool; the Incus-based neighbours all stop at system containers and iptables/nftables.
